# 31 — Numeric and Protected Identifier Reference

Status: Implemented reference decision  
Last reviewed: 2026-08-17  
Owners: Architecture, security, database and API

## Decision

BOOKDOC2026 uses a deliberate mixed internal identifier policy and one consistent public boundary:

- ASP.NET Core Identity user and role models use `uint` CLR identifiers, following the SDTS identity design;
- tenant, stakeholder, patient, resource, scheduling and other business aggregates use positive signed `long` identifiers;
- SQL Server stores these values as `bigint` where required because it has no unsigned integer type;
- public API routes, requests and responses expose protected opaque `string` identifiers instead of raw numeric keys.

`ulong` is not used for SQL-owned aggregate keys because it has no native SQL Server representation and would require conversions with ordering/query/interoperability risks. `ushort`, `byte`, `short` or `int` may be used for genuinely bounded enums/reference values after capacity and compatibility are documented; they are not the default aggregate identity. This preserves the useful SDTS internal typing and the requested encrypted-string DTO boundary without copying unsigned types indiscriminately.

Human-facing numbers such as patient number, invoice number, receipt number and queue token remain separate scoped business identifiers. A protected public ID is not a display number.

## Identifier categories

| Category | Representation | Examples |
|---|---|---|
| Identity primary/foreign key | `uint` CLR / SQL `bigint` mapping | user, role and their assignments/claims |
| Business entity primary/foreign key | positive `long` / SQL `bigint` | tenant, branch, stakeholder, patient, service, resource, hold |
| Public entity reference | protected `string` | route IDs and DTO `Id`, `PatientId`, `ResourceId` fields |
| Idempotency identifier | `Guid` / SQL `uniqueidentifier` | patient registration request, scheduling hold request |
| Version/concurrency value | `long` | expected version and response version |
| Bounded enum/reference value | selected `byte`/`ushort`/`short`/`int` | state or compact catalog code only when its range is proven |
| Business number | scoped string generated by owning module | patient, invoice, receipt and queue numbers |
| Correlation identifier | opaque string | trace and log correlation |

## Numeric generation

`NumericId` creates a positive 63-bit, time-ordered identifier before persistence. Its layout reserves 41 bits for milliseconds since 2026-01-01 UTC, 10 bits for a writer node and 12 bits for the per-millisecond sequence. This supports aggregate construction without database round trips and keeps insert/index locality substantially better than random GUID keys.

Every concurrently active writer of application-generated business IDs must have a unique `NumericIds:NodeId` from 0 through 1023. API and its hosted Worker-library services share the API instance's node. Production deployment configuration must allocate and validate a unique node ID for every API instance; reusing a node concurrently can create duplicate keys. Clock monitoring is mandatory. Identity user/role IDs follow the Identity store's generated-key behavior and are not produced by `NumericId`.

EF marks entity IDs `ValueGeneratedNever`; the application-generated number is always inserted. Idempotency GUIDs remain client/request-generated and continue to have unique constraints.

## Public protection boundary

`IPublicIdCodec` protects and unprotects IDs by resource kind and tenant scope. The protected payload contains a format version, tenant scope and numeric ID. Separate Data Protection purposes prevent a Patient token from being accepted as a Resource token. Tenant-scoped decoding rejects a valid token from another tenant.

Special scopes include:

- tenant-application tokens are platform scoped;
- tenant tokens are self-scoped;
- identity-subject tokens are platform scoped and hide the underlying `uint` user ID;
- user-scope tokens are tenant scoped;
- every other current public entity token requires its owning tenant scope.

Controllers decode public route/query values before calling application services. Application services decode referenced IDs in request DTOs and encode response DTOs. Domain entities, repositories and EF never accept protected strings. Invalid, tampered, wrong-kind or wrong-tenant values fail with `invalid_identifier`; they must not be silently converted to zero or treated as missing.

Protection does not grant authorization. Every request must still pass host access, permission, tenant and branch checks. Protected values must not be logged as trusted identity evidence.

## Data Protection operations

All API instances that encode public IDs must use the same Data Protection application name and accessible protected key ring. Worker-library services run inside those API instances. Development defaults to `%LocalAppData%/BookDoc2026/DataProtectionKeys`; production must use an explicitly secured shared key store suitable for the hosting platform.

Key-ring requirements:

- encrypt keys at rest and restrict access to the application identity;
- back up and restore keys with the service recovery plan;
- retain old keys while issued URLs, queued payloads or stored references may still be used;
- rotate keys through Data Protection lifecycle controls, not by deleting the ring;
- test cross-instance decode, backup restore and rotation before pilot;
- never commit keys, protected production IDs, credentials or patient data.

Protection is probabilistic: encoding the same internal ID more than once can produce different strings. Clients must treat IDs as opaque and may compare a value within one response/workflow, but must not infer order, parse it, or depend on ciphertext being regenerated identically. Previously issued tokens remain decodable while the required keys are retained.

## Migration and compatibility

The local development database contained no business data, so the six GUID-era development migrations were replaced by `NumericKeyBaseline`. This is a clean pre-production baseline, not a production conversion procedure. A populated GUID database would require a reviewed mapping table, dual-reference/backfill strategy, foreign-key reconciliation, cutover and rollback plan.

Legacy source identifiers remain in migration staging/crosswalk data when migration begins. They are never exposed as new primary keys merely to preserve legacy parity.

## Verification gates

- Identity user/role IDs remain `uint` in CLR and round-trip through the SQL Server `bigint` mapping.
- Business aggregate IDs and foreign keys are positive signed numeric types.
- Public contract entity IDs are strings; only approved request/idempotency GUIDs remain.
- Route, query and request decoding rejects tampering, wrong resource kinds and cross-tenant reuse.
- Authorization and tenant/branch scope execute in addition to token validation.
- Numeric generation is positive, unique and increasing under representative concurrency.
- SQL migrations create application-generated non-identity `bigint` business keys, Identity-generated user/role `bigint` keys and retain `uniqueidentifier` only where intended.
- API instance node assignments are unique in every deployment topology; hosted Worker-library services use the containing API node.
- Shared key-ring, rotation and restore tests pass before production.
